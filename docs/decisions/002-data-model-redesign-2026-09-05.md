# 002 · 데이터 모델 재설계의 네 가지 갈림길

- **일시** 2026-09-05
- **결정한 사람** 소유자(여동현)
- **관련** 이슈 #6 · [`erd.md`](../erd.md) · [`api.md`](../api.md) · 이슈 #11(마이그레이션) · #12(API)

## 결정 네 줄

1. **「사람」과 「신청」을 두 테이블로 나눈다.** `applicant`(신원) + `application`(회차별 신청).
2. **정원의 정본은 코드(`src/lib/event.ts`)다.** DB `slot.capacity`는 거기서 시드된 사본이다.
3. **참가자 링크는 하나로 합친다.** `/me/[token]` 하나를 알림톡으로 보내고, 화면이 상태를 보고 바뀐다.
4. **백필하지 않는다.** 프로덕션 신청자 0건이라 새 스키마를 깨끗하게 세운다.

---

## 1. 사람과 신청을 나눈 이유

지금 `applicant` 한 장에 이름·전화 같은 **신원**과 자리·기한·토큰 같은 **이번 행사 상태**가
섞여 있다. `phone`이 UNIQUE라서, 2차 행사가 열리면 **1차에 참가했던 사람이 신청을 못 한다.**
전화번호가 이미 있기 때문이다.

UNIQUE를 푸는 것으로는 안 된다 — 그러면 같은 사람이 1차에 두 번 신청하는 것도 열린다.
`(전화, 회차)` 복합키로 바꾸는 방법도 있지만, 그때는 이미 실데이터가 쌓여 있어
지금보다 위험하다.

**기각한 대안** — 한 테이블에 `event_no` 컬럼만 추가.
같은 사람의 이름·생년월일이 회차마다 복사돼 쌓이고, 한 명이 두 번 참가하면
「같은 사람인가」를 전화번호 문자열 비교로 판단해야 한다.

대가는 조회할 때 조인 한 번인데, 운영자 목록이 20~수백 행 규모라 체감이 없다.

## 2. 정원의 정본을 코드로 정한 이유

숫자 `10`이 두 곳에 **따로** 적혀 있었다.

| 어디 | 무엇이 읽나 |
|---|---|
| `src/lib/event.ts:29` `capacityPerGender: 10` | 화면 문구 14곳 — 홈 "20명", 신청 폼 "남 10 · 여 10", FAQ, 환불 문구, 구글 검색 카드 |
| `db/migrations/001:84` `insert into gender_slot ... 10` | **마감 판정** — `update ... where taken < capacity` |

지금은 둘 다 10이라 문제가 없다. 사고는 **정원을 바꾸는 순간** 난다. 코드만 고치면
화면은 늘어난 정원을 광고하는데 실제로는 옛 정원에서 마감된다. DB만 고치면 반대가 된다.
마이그레이션은 한 번만 실행되므로 `event.ts`를 고쳐도 DB 행은 영원히 안 바뀐다.

**코드를 정본으로 정했다.** 정원은 장소 계약과 진행표(1대1 대화 10회)에 묶인 값이라
운영 중에 바뀔 일이 사실상 없고, 화면 문구와 절대 어긋나지 않는 쪽이 더 중요하다.

**기각한 대안** — DB를 정본으로 두고 운영자가 화면에서 조정.
홈·행사 페이지의 "20명"이 매 접속마다 DB를 읽어야 해서, 지금 정적으로 뜨는 페이지가
동적으로 바뀐다. 얻는 것(정원 변경 자유)보다 잃는 것(첫 화면 속도)이 크다.

⚠️ `slot.capacity`는 DB에 **남는다.** 선착순을 막는 한 줄 UPDATE 안에서 비교돼야 하기 때문이다.
`npm run db:migrate`가 `event.ts` 값을 upsert하고, 어긋나면 `/admin`이 빨간 경고를 띄운다.

## 3. 링크를 하나로 합친 이유

지금은 한 사람에게 링크가 3개 나간다 — `/pre/xxx`(자리 확보), `/q/yyy`(사전질문),
현장용 `site_token`(화면도 없다). 운영자가 단계마다 **다른 링크를 찾아** 보내야 한다.

소유자 결정: 마이페이지에서 어차피 전부 처리하므로, **알림톡에는 마이페이지 링크 하나만**
보낸다. 화면이 상태를 보고 「입금 안내」→「사전질문」→「현장」으로 알아서 바뀐다.

**문항 보호가 약해지지 않는다.** 지금도 실제 방어선은 토큰이 아니라 상태 검사다 —
`/api/q`는 `status='confirmed'`가 아니면 문항을 안 준다. 새 구조도 같다:
`stage === 'questions'`(= 입금 완료)일 때만 문항이 내려간다.

**기각한 대안** — 단계별 토큰 유지. 링크 하나가 유출돼도 그 단계만 노출되는 게
유일한 장점인데, 대신 사람마다 링크 3개를 발급·재발송·추적해야 하고
알림 테이블도 「어느 링크를 보냈나」를 따로 기록해야 한다.

## 4. 백필하지 않는 이유

계획서(§2단계)는 "프로덕션에 사전등록 데이터가 쌓이는 중"을 전제로 **drop 금지 + 백필
스크립트 + 전환 시점 문서**를 요구했다. **전제가 틀렸다.** 2026-09-05 실측:

```
applicant           0건
gender_slot         M 0/10 · F 0/10
schema_migration    001 · 002 · 003 · 004  ← 4건 모두 기록됨
```

옮길 데이터가 없으므로 백필 스크립트도, 전환 시점 결정도 필요 없다. 005에서 옛 표를
drop하고 새로 세운다.

**덤으로 위험 하나가 사라졌다.** `architecture.md` §1.1이 경고하던 "003 재실행으로
답변·참가자 표가 사라진다"는 사고는 `schema_migration`에 001~004가 기록돼 있어
일어나지 않는다. `npm run db:migrate`를 안심하고 돌릴 수 있다.

🔴 **005를 적용하기 직전에 위 세 줄을 다시 확인한다.** 그 사이에 신청자가 생겼다면
이 결정의 근거가 사라지고 백필이 필요해진다.

## 이 결정이 기대는 것 (깨지면 결정도 깨진다)

- 🔴 **`slot`의 한 줄 UPDATE.** `update slot set taken=taken+1 where taken<capacity`가
  선착순의 전부다. 「먼저 읽고 나중에 쓰기」로 바꾸면 그 사이에 남이 끼어들어 정원이 넘는다.
- 🔴 **`payment.application_id`의 `on delete set null`.** 신원은 3년, 결제 기록은 법정 5년이라
  보유기간이 다르다. cascade로 되돌리면 3년 파기 때 결제 기록이 함께 날아가
  전자상거래법 제6조 위반이 된다.
- 🔴 **`answer.form_version`.** 문항이 바뀌면 과거 답의 뜻이 통째로 달라진다.
  버전 없이 저장하면 리포트를 쓸 때 복원할 수 없다.
