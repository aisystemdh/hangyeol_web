## 2. 🔴 입금 기한의 기준점을 옮긴다 (001을 대체)

`001`은 「폼 제출 시각」으로 정했고 근거는 이랬다:

> 알림톡을 **일괄 발송**하므로 발송 시각 기준으로 잡으면 링크를 늦게 여는 사람의 시간이
> 통째로 깎인다. 그건 손님이 통제할 수 없는 손해다.

**그 전제가 사라졌다.** 결정 7로 발송이 개인별 수동이 되었으므로, 운영자가 그 사람에게 보내는
순간과 그 사람이 받는 순간이 거의 같다. 일괄 발송에서 생기던 손해가 없다.

### 이 변경이 001의 숙제를 푼다

`001`은 이렇게 적었다 — *"알림톡을 보내는 시점에는 **그 사람의 마감 시각이 아직 존재하지
않는다**"*. 그래서 T1 문구를 「3일」로 뭉뚱그렸고, 전체 마감(10/17 23:59)에 걸려 72시간을
못 받는 **10/15~17 제출자는 소유자가 직접 개별 안내**하기로 했다.

발송 시점에 기한이 확정되면:

- T1의 `#{입금기한}` 변수에 **실제 날짜·시각**을 넣을 수 있다.
- 전체 마감에 걸리는 사람도 **정확한 시각이 자동으로 찍힌다.**
- 🔴 **10/15~17 수동 안내가 불필요해진다.**

### 대신 새로 생기는 것

- 기한은 **템플릿에 달린 `starts_due_at` 플래그**로 시작된다(§3). 그 템플릿을 보내야 시계가 돈다.
- 운영자가 발송을 잊으면 그 사람은 기한이 없는 채로 남는다 → **「오늘 보낼 것」 목록이
  유일한 안전장치**다. `001`이 기대던 「운영자 화면의 기한 칸」이 더 중요해졌다.
- `dueAtFrom()`은 그대로 쓴다 — 개인 72h와 전체 마감 중 **먼저 오는 쪽**이라는 규칙은 유지된다.

## 3. 알림톡 문구를 DB에 둔다 (결정 9)

### 왜

문구는 **바뀐다.** 대표 검토, 카카오 심사 반려, 회차별 날짜 변경으로 바뀐다.
코드 상수로 두면 그때마다 배포가 필요하고, 운영자(비개발자 3인)가 스스로 못 고친다.

### 표

```sql
create table notification_template (
  id            text        primary key,        -- 'T1'~'T13' 또는 운영자가 붙인 코드
  label         text        not null,           -- 「신청 감사 + 계좌 안내」 — 목록에 보이는 이름
  body          text        not null,           -- #{이름} 같은 변수 자리를 포함한 문구
  channel       text        not null default 'manual'
                  check (channel in ('manual','alimtalk','sms','email')),
  when_hint     text,                           -- 「신청 직후」 — 화면 정렬·추천용
  starts_due_at boolean     not null default false,  -- 🔴 §2. 이걸 보내면 72시간이 시작된다
  approved_code text,                           -- 카카오 심사 통과 코드(대행사 붙은 뒤)
  sort_order    smallint    not null default 0,
  active        boolean     not null default true,
  updated_by    text,
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);
```

시드는 지식베이스 `한결_알림톡_템플릿_13건.md`의 T1~T13.

### 지켜야 할 것 넷

- 🔴 **`starts_due_at`은 한 번에 하나만 `true`여야 한다.** 둘이면 나중에 보낸 쪽이 기한을
  덮어써서 손님의 시간이 줄어든다. 부분 유니크 인덱스로 못 박는다:
  `create unique index on notification_template ((true)) where starts_due_at and active;`
- 🔴 **발송 기록(`notification.body`)에는 그때 보낸 문구를 복사해 둔다.** 템플릿을 나중에
  고쳐도 과거 기록이 따라 바뀌면 안 된다 — 분쟁 시 "무엇을 보냈다고 주장하는지"가 사라진다.
- 🔴 **문구에 계좌번호를 직접 쓰지 않는다.** `#{계좌}` 변수를 쓴다. 값을 13곳에 박으면
  계좌가 바뀔 때 하나가 반드시 빠지고, `biz.ts`가 지키는 「값은 환경변수에서만」이 DB로 새어나간다.
- ⚠️ **`render()`가 채우지 못한 변수(`missing`)가 있으면 「보냄」 버튼을 잠근다.**
  `「#{계좌}」`가 그대로 박힌 문구가 손님에게 나가는 사고를 막는다. `biz.missing`과 같은 원칙.

### 변수 목록

`#{이름}` `#{닉}` `#{입금액}` `#{입금자명}` `#{입금기한}` `#{은행}` `#{계좌}` `#{예금주}`
`#{링크}` `#{행사일}` `#{시간}` `#{장소}` `#{상대이름}`

### ⚠️ KB 템플릿 3건이 새 흐름과 어긋난다

심사에 넣기 전에 고쳐야 한다 — 통과한 문구는 변수 자리 말고 못 바꾼다.

| 템플릿 | 지금 문구 | 왜 사실이 아닌가 |
|---|---|---|
| T2 | "자리 확보 완료 · 입금 안내" | 새 흐름에서 **자리는 입금해야 잡힌다.** 정식등록만으로는 자리가 없다 |
| T5 | "정원 마감 · 대기 안내" | 정원이 차도 신청을 계속 받는다 |
| T6 | "기한이 지나 **자동으로** 취소되었습니다" | 🔴 자동 취소가 없다(결정 3) |

T1·T2를 「신청 감사 + 계좌 + 정식등록」 한 건으로 합치는 것이 맞아 보인다. **대표 확인 필요** —
구현과 병렬로 진행한다.

## 5. 데이터 모델

옛 표를 drop하고 새로 세운다. 🔴 `db/migrate.mjs`는 **파일 하나가 한 트랜잭션**이므로
drop과 create를 같은 파일(`005_rebuild.sql`)에 둔다 — 쪼개면 중간 실패 시 표가 절반만 남는다.

**사라지는 표**: `gender_slot`(결정 1) · `participant`(→`application.nick`) ·
`applicant_event`(→`event_log`) · `answer_pre`(→`answer`) · `recruit_display`(→`event.hw_*`)

| 표 | 핵심 |
|---|---|
| `event` | 회차. `date`는 `EVENT.dateISO`의 **사본** · `hw_m`/`hw_f` 공개 워터마크(내려가지 않음) |
| `applicant` | 신원만. `phone UNIQUE` · 🔴 나이 컬럼 금지(항상 `ageOn(birth)`) |
| `application` | 중심 표. 아래 |
| `answer` | `form`(`pre`·`round`·`part2`·`self`·`exit`·`like`) · `round` · `form_version` · `a jsonb` |
| `payment` | `application_id` **on delete set null** + `event_id` 별도 보유 |
| `notification_template` | §3 |
| `notification` | 발송 **기록**(큐 아님). `template_id` · `body`(복사본) · `sent_at` · `sent_by` |
| `event_log` | `kind` · `actor` · `meta jsonb` |
| `report` | `pdf_url` · `published_at` — 리포트는 PDF를 올리고 링크만 준다 |
| `purge_log` | `rule` · `subject_id` — 🔴 개인정보를 적지 않는다 |

**`application`**
```
id · applicant_id→applicant(cascade) · event_id→event
status 'applied'|'paid'|'canceled'   seq bigserial   token UNIQUE   token_issued_at
정식등록  registered_at · marital · job · email · depositor_name
동의      privacy/marketing/truth/refund/email _agreed_at   (전부 timestamptz)
입금      notified_at(기한 시작 알림톡 발송 시각) · due_at · paid_at · nick
유입      source · utm jsonb · referrer · landing_path
운영      memo · created_at · updated_at
UNIQUE(applicant_id, event_id)   UNIQUE(event_id, nick) where nick is not null
```

### 되돌리면 깨지는 제약 넷

- 🔴 `payment.application_id`는 **`on delete set null`.** 신원은 3년 파기(화면에 고지),
  결제 기록은 **법정 5년 보존**(전자상거래법 §6). cascade면 3년째에 위반이 된다.
  `payment.event_id`를 따로 들어 끊긴 뒤에도 회차 매출이 남게 한다.
- 🔴 `answer`의 부분 UNIQUE **두 개**:
  `unique (application_id, form) where form <> 'round'` +
  `unique (application_id, round) where form = 'round'`.
  하나로 합치면 Postgres가 NULL을 서로 다르게 봐서 **새로고침 두 번으로 중복 제출이 뚫린다.**
- 🔴 `check ((form = 'round') = (round is not null))` — round가 엉뚱한 폼에 섞이는 것을 DB가 막는다.
- 🔴 `answer.form_version` — 문항이 바뀌면 과거 답의 뜻이 통째로 달라진다.
  `form9-copy.ts`에 `FORM_VERSION` 상수를 둔다.

## 6. 손님이 지나는 길

```
1. /events/1 신청 폼 ──────────────▶ status=applied · token 즉시 발급
2. 운영자: 템플릿 선택 → 문구 생성 → 복사 → 카톡 발송 → 「보냄」
                    ▲ starts_due_at 템플릿이면 이 순간 due_at = now + 72h (전체 마감이 먼저면 그쪽)
3. 손님: /me/[token] 정식등록(혼인·직업·이메일·입금자명·환불동의) → 계좌 확인
4. 입금 → 운영자 「입금 확인」 ─▶ status=paid · 닉(결N) 배정 · 여기서부터 20자리
5. 운영자: 확정 안내 → 사전질문 링크 발송
6. 손님: /me 에서 사전 10문항
7. D-2 · D-1 · 당일 · T+1 · T+3 · T+5 — 때 되면 운영자가 골라서 발송
```

**마이페이지 `/me/[token]`** — 대시보드 + 하위 화면
`register` · `payment` · `questions` · `confirmed` · `onsite` · `review` · `report` ·
`canceled` · `closed` · `ended`

### 🔴 정보 노출 규칙 — 이 재설계에서 가장 조심할 곳

| 화면 | 내려간다 | 절대 안 내려간다 |
|---|---|---|
| `register` | 사업자 신원 · 환불 규정 · 금액 | **계좌번호** · 문항 |
| `payment` | 계좌 · 예금주 · 기한 · 금액 | 문항 |
| `questions` | **문항 전문 + pairedIndexes + form_version** | 계좌 |
| 그 밖 | 안내 문구만 | 계좌 · 문항 |

- 🔴 **문항 방어의 실체는 토큰이 아니라 `status === 'paid'`다.** 토큰이 하나로 합쳐져
  노출면이 넓어졌으므로 `QUESTIONS`를 참조하는 코드에 **도달조차 못 하게** 한 곳으로 좁힌다.
- 🔴 **DB row를 스프레드(`...row`)하지 않는다.** 필드를 하나씩 골라 담는다 — 컬럼을 추가할 때
  조용히 새는 유일한 경로다.
- 🔴 **마이페이지를 서버 컴포넌트로 만들어 문항을 props로 넘기지 않는다.**
  `import "server-only"`는 **번들 포함만** 막지 RSC 페이로드 직렬화는 못 막는다.
  클라이언트가 `GET /api/me/[token]`으로 가져오게 한다.
- ⚠️ `biz.ts`를 `bizIdentity()`와 `bizAccount()` 둘로 쪼갠다. 지금은 토큰만 맞으면 계좌가 항상 내려간다.

## 7. 운영자 페이지

`Board.tsx`는 **버린다**(상태 9개 전제라 남는 게 거의 없다). 셋은 반드시 가져온다:

  `[전화번호 복사] [문구 복사] [보냄 ✓]`. 상단에 **「오늘 보낼 것」**

## 8. 이 결정이 기대는 것 (깨지면 결정도 깨진다)

- 🔴 **「오늘 보낼 것」 목록.** 자동화를 전부 걷어냈으므로 운영자가 잊으면 아무 일도 안 일어난다.
  기한 임박·확정 후 미발송·오늘이 D-2인지를 화면이 대신 기억한다.
- 🔴 **운영자 목록의 「기한」 칸.** `001`이 명시적으로 기대던 장치이고, 자동 만료가 없어진 지금
  더 중요해졌다. `hours_left`와 12시간 미만 강조를 반드시 옮긴다.
- 🔴 **`db.ts`의 `max: 10`.** 선착순이 사라졌다고 동시성이 사라진 게 아니다 — 인스타 게시물
  직후 신청이 몰리는 것은 그대로다(`max:1`에서 27건 중 8건 사망, 2026-08-29 실측).
- 🔴 **`middleware.ts`**(`/admin/:path*`, `/api/admin/:path*`). 지금은 라우트마다 `isAdmin()`을
  손으로 부르는데 하나만 빠뜨리면 참가자 20명의 이름·연락처·생년월일이 샌다.
  라우트의 `isAdmin()`은 이중 방어로 남긴다.
- 🔴 **`/api/recruit`만 `{ok,data}` 봉투를 씌우지 않는다.** `RecruitStatus.tsx:31`이 `d.message`를
  최상위에서 읽고 없으면 **에러 없이 아무것도 안 그린다** — 홈의 「모집 현황」 줄이 조용히 사라진다.
- 🔴 **`SiteChrome.tsx`에 `/me/`를 추가한다.** 안 하면 마이페이지에 헤더와 「1차 모임 신청」
  고정 바가 붙어, 이미 신청한 사람에게 다시 신청하라고 권하는 화면이 된다.
- 🔴 **`admin-data.ts`를 1단계에서 함께 지운다.** `participant`·`gender_slot`을 조인하므로
  남겨두면 **빌드·타입 검사는 전부 통과하고** 런타임에 `42P01`로 `/admin`이 통째로 500이 된다.
