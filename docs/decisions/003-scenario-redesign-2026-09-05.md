## 2. 입금 기한은 「신청 폼을 낸 시각 + 72시간」 (001 유지)

초안은 이걸 「알림톡 발송 시각」으로 옮기려 했다. 발송이 개인별 수동이 되었으니 보내는 순간과
받는 순간이 같아진다는 논리였다. **검토에서 뒤집혔다.**

신청 시각을 기준으로 하는 이유 셋:

1. **신청 완료 화면에서 곧바로 기한을 보여줄 수 있다.** 발송 기준이면 그 화면에서는 아직
   그 사람의 기한이 존재하지 않는다.
2. **알림톡이 실패해도 기한이 흔들리지 않는다.** 발송 기준이면 실패한 사람은 기한 없이
   방치되고, 운영자가 눈치채야만 시계가 돈다.
3. 정식등록 시각 기준(세 번째 안)은 **등록만 안 하면 무한정 기다리는 구멍**을 만든다.

🔴 **그래서 결정 7의 예외가 붙는다 — 입금 안내만은 자동으로 나간다.** 신청 폼이 저장되는
순간 시스템이 바로 보낸다. 운영자가 손으로 보내면 밤 11시에 신청한 사람은 다음 날 아침에
안내를 받고 **72시간 중 아홉 시간을 이미 잃은 채** 시작한다.

### 이 결정이 지우는 것

- 초안이 만들려던 **템플릿의 「이걸 보내면 시계가 시작된다」 표시와 그 부분 유니크 인덱스가
  전부 불필요해진다.** 기한은 신청에서 나오지 발송에서 나오지 않는다.
- 🔴 **전체 마감(행사 7일 전)을 지금은 쓰지 않는다**(소유자 확정 — 「지금 만드는 시나리오가
  우선이고 필요해질 때 고친다」). 날짜로 신청을 막는 장치와 기한을 잘라내는 계산을 **코드에서
  지운다.** 안 쓰는 채로 남겨두면 다음 사람이 아직 살아 있는 규칙으로 읽는다.
- 그래서 기한 계산은 **「신청 시각 + 72시간」 한 줄**이 된다.

### 대기자에게는 기한이 없다

이건 물어서 정한 게 아니라 위 결정들에서 따라 나온 것이다. 대기자는 자리가 없어 입금 안내를
받지 못하므로(§3의 2번을 대신 받는다) **시계를 돌리지 않는다.** 앞의 누군가가 취소해 자리가
나고 입금 안내를 받는 순간 72시간이 시작된다.

## 3. 알림톡 아홉 가지

### 목록

| # | 언제 | 무엇을 알리나 | 누가 |
|---|---|---|---|
| 1 | 신청 폼이 저장되는 순간 | **입금 안내** — 마이페이지 링크 · 금액 · 기한 | 🔴 **자동** |
| 2 | 정원이 이미 찼을 때 신청 | **대기 명단 등록** — 자리가 나면 연락드린다 | 운영자 |
| 3 | 기한 12시간 전쯤 | **입금 기한 임박** | 운영자 |
| 4 | 운영자가 입금 확인 | **자리 확보 완료 + 사전질문 요청**(한 건) | 운영자 |
| 5 | 행사 3일 전쯤 | **사전질문 미제출 안내** | 운영자 |
| 6 | 행사 전날 | **행사 안내** — 시간 · 장소 · 준비물 | 운영자 |
| 7 | 행사 다음 날 | **후기 안내** | 운영자 |
| 8 | 환불한 뒤 | **환불 완료** — 금액 · 날짜 | 운영자 |
| 9 | 리포트가 나온 뒤 | **리포트 안내** — 링크 | 운영자 |

- 🔴 **기한이 지났는데 입금이 없는 사람에게는 알림톡을 보내지 않는다.** 운영자가 개인적으로
  연락한다(소유자 결정). 그래서 「자동으로 취소되었습니다」류의 문구는 만들지 않는다.
- **대기자에게 자리가 났다는 안내는 1번을 다시 보낸다.** 필요한 정보가 똑같아 따로 만들지 않는다.
- 알림톡은 **안내만** 보낼 수 있다. 「다음 회차도 신청하세요」 같은 권유는 광고라 심사에서 막힌다.

### 뿌리오 규격 (2026-09-05 개발 문서 실측 — `bizppurio.github.io`)

이 규격이 아래 표의 모양을 정한다. 문서를 읽고 **설계에 없던 것 셋**이 드러났다.

- **토큰** — `POST https://api.bizppurio.com/v1/token`, `Authorization: Basic`. **24시간짜리**다.
  발송마다 새로 받지 말고 캐시한다.
- **발송** — `POST https://api.bizppurio.com/v3/message`, `Authorization: Bearer`.
  ```json
  { "account": "...", "refkey": "<우리 발송 기록 id>", "type": "at",
    "from": "<발신번호>", "to": "<받는 번호>",
    "content": { "at": { "senderkey": "...", "templatecode": "...",
                         "message": "<변수가 전부 채워진 최종 본문>",
                         "button": [ ... ] } },
    "resend": { "first": "sms" },
    "recontent": { "sms": { "message": "<90바이트 이내 대체 문구>" } } }
  ```
- 🔴 **`message`는 「변수를 다 채운 최종 본문」이다.** 뿌리오는 `#{}`를 대신 채워주지 않는다.
  못 채운 변수가 남으면 **`#{계좌}`가 그대로 손님에게 간다.** 「미치환이면 발송을 막는다」가
  선택이 아니라 필수인 이유가 이것이다.
- 🔴 **템플릿에 버튼이 있으면 발송 요청에도 같은 버튼을 넣어야 한다.** 그래서 **버튼 정의를
  문구 행에 함께 저장한다**(설계 초안에 없던 것 ①).
- 🔴 **대체문자 문구를 따로 들어야 한다**(설계 초안에 없던 것 ②). 알림톡이 실패하면
  `recontent.sms.message`가 나가는데 **90바이트**뿐이라 본문을 그대로 쓸 수 없다.
  자동으로 잘라내면 문장 중간에서 끊긴다 — 사람이 짧게 따로 쓴다.
- 🔴 **동기 응답의 `code: 1000`은 「접수됨」이지 「손님이 받았다」가 아니다.**
  실제 도달은 **웹훅**으로 따로 온다(`RESULT: 4100`이 도달). 그래서 **결과를 받는 공개 주소가
  하나 필요하다**(설계 초안에 없던 것 ③). 우리가 보낸 `refkey`가 그대로 돌아오므로
  발송 기록 id를 refkey로 쓰면 짝이 맞는다. `messagekey`는 중복 방지용으로 함께 저장한다.
- **발신 프로필 키(`senderkey`)와 발신번호(`from`)는 회차·문구와 무관하게 하나**뿐이므로
  DB가 아니라 **환경변수**에 둔다.
- 템플릿 등록은 API로도 되지만(`/v3/kakao/template/add`) **소유자가 카카오톡 설정 화면에서
  직접 한다.** 우리는 승인받은 코드를 문구 행에 적기만 한다. 심사 상태는 REG → REQ → APR/REJ.
- 길이 — 템플릿 964자, 발송 본문 1,300자.

### 표

```sql
create table notification_template (
  id            text        primary key,        -- 운영자가 붙인 코드
  label         text        not null,           -- 목록에 보이는 이름
  body          text        not null,           -- #{이름} 같은 변수 자리를 포함한 문구
  channel       text        not null default 'alimtalk'
                  check (channel in ('alimtalk','sms','email')),
  when_hint     text,                           -- 「신청 직후」 — 화면 정렬·추천용
  auto_send     boolean     not null default false,  -- 🔴 1번만 true
  template_code text,                           -- 심사 통과 후 받는 코드(뿌리오 templatecode)
  approval      text        not null default 'REG'   -- REG · REQ · APR · REJ
                  check (approval in ('REG','REQ','APR','REJ')),
  buttons       jsonb,                          -- 🔴 템플릿에 버튼이 있으면 발송에도 같이 보낸다
  sms_body      text,                           -- 🔴 대체문자 문구(90바이트 이내). 자동으로 자르지 않는다
  sort_order    smallint    not null default 0,
  active        boolean     not null default true,
  updated_by    text,
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);
```

**발송 기록(`notification`)이 들어야 하는 것**: 대상 신청 · 문구 id · **보낸 문구 전문 복사본** ·
`refkey`(= 이 기록의 id) · `messagekey`(뿌리오가 준 것) · **접수 결과**(동기 `code`) ·
**도달 결과**(웹훅 `RESULT`) · 도달 시각 · 보낸 사람 · 만든 시각.
🔴 접수와 도달을 **한 칸에 뭉치지 않는다** — 접수는 됐는데 도달이 안 된 경우가 실제로 있고,
그때 운영자가 봐야 하는 것은 「보냈다」가 아니라 「안 닿았다」다.

### 지켜야 할 것 넷

- 🔴 **발송 기록에는 그때 보낸 문구를 복사해 둔다.** 템플릿을 나중에 고쳐도 과거 기록이 따라
  바뀌면 안 된다 — 분쟁 시 "무엇을 보냈다고 주장하는지"가 사라진다.
- 🔴 **발송 결과를 남긴다** — 성공 / 실패 / 문자로 대체 발송. 실패는 운영자 화면 위쪽에
  「보내다 실패한 것」으로 모아 보여준다. **자동 재시도는 하지 않는다**(같은 안내가 두 번 가면
  손님이 기한을 헷갈리고, 번호 오류라면 몇 번을 보내도 똑같이 실패한다).
- 🔴 **계좌번호를 문구에 아예 넣지 않는다.** 링크로만 보낸다. 계좌를 문구에 박으면
  **계좌가 바뀔 때 아홉 개를 다시 심사받아야 한다**(통과한 문구는 못 고친다).
  그래서 계좌 관련 변수 셋을 목록에서 뺐다.
- ⚠️ **채우지 못한 변수가 남아 있으면 「보냄」 버튼을 잠근다.** 뿌리오는 `#{}`를 대신 채워주지
  않으므로, 막지 않으면 `「#{계좌}」`가 그대로 박힌 문구가 손님에게 나간다.
- 🔴 **본문에 링크를 글자로도 넣는다.** 버튼만 두면 안 된다 — **문자로 대체 발송되면 버튼이
  통째로 사라진다.** 그러면 「아래에서 확인하세요」라고 써놓고 갈 곳이 없는 문자가 나간다.
  모든 문구에 `▶ #{링크}` 줄을 둔다. 덕분에 **대체 문자 문구를 따로 안 써도 된다**(본문 그대로).
  `sms_body`는 따로 쓰고 싶을 때만 채우는 칸으로 남긴다.
- 🔴 **버튼 주소에는 변수를 못 쓴다.** `url_mobile`은 완성된 주소여야 한다.
  보낼 때 **그 사람의 주소를 통째로 만들어** 넣는다. 도메인은 고정, 뒤의 토큰만 다르다.
- ⚠️ **토큰을 짧게 유지한다.** `#{링크}`가 문자에 글자 그대로 찍힌다. 길면 문자 한 통이
  길어지고 손님이 보기에도 지저분하다.

### 변수 아홉 개

`#{이름}` `#{입금액}` `#{입금기한}` `#{링크}` `#{행사일}` `#{시간}` `#{장소}` `#{환불액}` `#{처리일}`

초안에 있던 `#{닉}`·`#{입금자명}`·`#{은행}`·`#{계좌}`·`#{예금주}`·`#{상대이름}`은 **뺐다.**
계좌 셋은 위 이유로 안 쓰고, 닉네임은 현장에서 주기로 했고(결정 14), 상대 이름을 알려주는
안내는 이번 범위에 없다. **심사를 통과하면 못 고치니 안 쓸 변수는 지금 뺀다.**

반드시 하나가 낡는다.

### 공개 워터마크를 폐기한다

지금 홈의 모집 현황은 「한 번 올라간 숫자는 내려가지 않는」 값을 쓰고, **남은 자리 = 정원 −
그 값**으로 계산한다. 입금완료가 3명인데 값이 8이면 화면에 「여성 2자리」가 뜬다. 실제로는
일곱 자리가 남았다.

그 장치가 막던 것은 **선착순 시절 기한이 지나 자리가 되살아나면서 숫자가 뒤로 가던 일**이다.
결정 1·3이 그 원인을 없앴다. 이제 숫자가 내려가는 경우는 실제 취소뿐이고, 남은 것은
**잔여석을 실제보다 적어 보이게 하는 효과**뿐이다 — 표시광고법 §3①이 금지하는 쪽이다.

- 입금완료 인원을 **그대로** 보여준다.
- 「절반도 안 찼을 때는 숫자를 감춘다」는 규칙은 **그대로 가져간다.** 그건 거짓이 아니라 침묵이다.
- 마감 문구에서 **「대기 신청은 받습니다」를 뺀다**(대기 안내는 §3의 2번이 한다).

**`application`**
```
id · applicant_id→applicant(cascade) · event_id→event
status '신청함'|'입금완료'|'취소됨'   seq bigserial   token UNIQUE   token_issued_at
기한      created_at + 72h 를 계산해 due_at 에 **박아 둔다**(규칙이 바뀌어도 과거 기한은 안 변한다)
          🔴 대기자로 접수된 신청은 due_at 이 비어 있다
정식등록  registered_at · marital · job · email · depositor_name
동의      privacy/marketing/truth/refund/email _agreed_at   (전부 timestamptz)
확정      paid_at · nick(행사 며칠 전 일괄 배정)
화면      view_override — 🔴 운영자가 화면을 고정했을 때만 값이 있다(결정 13)
유입      source · utm jsonb · referrer · landing_path
운영      memo · created_at · updated_at
UNIQUE(applicant_id, event_id)   UNIQUE(event_id, nick) where nick is not null
```

**`money`** (결정 15)
```
id · application_id→application  on delete set null · event_id→event
kind '입금'|'환불'   amount int(원, 양수)   occurred_at   depositor_name   note
recorded_by   created_at
```

### 되돌리면 깨지는 제약 넷

- 🔴 `money.application_id`는 **`on delete set null`.** 신원은 3년 파기(화면에 고지),
  결제 기록은 **법정 5년 보존**(전자상거래법 §6). cascade면 3년째에 위반이 된다.
  `money.event_id`를 따로 들어 끊긴 뒤에도 회차 매출이 남게 한다.
- 🔴 `answer`의 부분 UNIQUE **두 개**:
  `unique (application_id, form) where form <> 'round'` +
  `unique (application_id, round) where form = 'round'`.
  하나로 합치면 Postgres가 NULL을 서로 다르게 봐서 **새로고침 두 번으로 중복 제출이 뚫린다.**
- 🔴 `check ((form = 'round') = (round is not null))` — round가 엉뚱한 폼에 섞이는 것을 DB가 막는다.
- 🔴 `answer.form_version` — 문항이 바뀌면 과거 답의 뜻이 통째로 달라진다.
  문항 정의 파일에 버전 상수를 둔다.

### 결정 16이 문항 정의에 요구하는 것

3년 뒤 **주관식 답만 지우고 선택지 답은 남기려면**, 저장된 답에서 둘을 구분할 수 있어야 한다.
🔴 **문항 정의에 「이 문항은 자유 서술인가」를 표시**하고, 답을 그 키로 저장한다.
표시가 없으면 파기 때 무엇을 지울지 알 수 없어 결국 전부 지우거나 전부 남기게 된다.

## 6. 손님이 지나는 길

```
1. 신청 폼 ──▶ 상태=신청함 · 토큰 발급 · 기한 = 지금 + 72시간
              │ 자리가 남았으면 → 입금 안내가 **자동으로** 나간다
              └ 자리가 찼으면   → 대기 명단 안내가 나가고 **기한은 안 붙는다**
2. 손님: /me/[token] 정식등록(혼인·직업·이메일·입금자명·환불동의) → 계좌 확인
3. 손님이 입금
4. 운영자가 은행 앱을 보고 「입금 확인」 ─▶ 상태=입금완료 · **여기서 자리 하나가 찬다**
                                        └ 같은 버튼이 돈 줄을 한 줄 쌓는다
5. 운영자: 자리 확보 + 사전질문 요청(한 건) 발송
6. 손님: /me 에서 사전 10문항
7. 행사 며칠 전: 스무 명에게 닉네임을 한 번에 배정
8. 전날 안내 → 당일 → 다음 날 후기 → 리포트
```

### 마이페이지가 무엇을 보여줄지 정하는 순서 (결정 13)

위에서부터 맞는 첫 화면을 보여준다. 원칙은 **「되돌릴 수 없는 사실이 위, 손님이 지금 해야 할
일이 아래」**다.

1. 취소됨 → 취소 안내
2. 행사가 끝났다 → 후기 · 리포트
3. 오늘이 행사날이다 → 당일 안내
4. 대기자다 → 대기 안내
5. 정식등록을 안 했다 → 등록 화면
6. 입금이 확인되지 않았다 → 계좌 · 금액 · 기한
7. 사전질문을 안 냈다 → 문항 열 개
8. 다 했다 → 확정 안내

🔴 **운영자가 화면을 고정하면 이 순서를 무시하고 그 화면이 나온다.** 고정된 신청은 운영자
목록에 **「화면 고정됨」** 표시가 뜬다 — 표시가 없으면 이것도 결국 잊는 장치가 된다.
고정은 운영자가 「자동으로 되돌리기」를 누를 때까지 유지된다.

### 🔴 정보 노출 규칙 — 이 재설계에서 가장 조심할 곳

| 화면 | 내려간다 | 절대 안 내려간다 |
|---|---|---|
| 등록 | 사업자 신원 · 환불 규정 · 금액 | **계좌번호** · 문항 |
| 입금 | 계좌 · 예금주 · 기한 · 금액 | 문항 |
| 사전질문 | **문항 전문 + 짝 정보 + 문항 버전** | 계좌 |
| 그 밖 | 안내 문구만 | 계좌 · 문항 |

- 🔴 **문항 방어의 실체는 토큰이 아니라 「입금완료」다.** 토큰이 하나로 합쳐져 노출면이
  넓어졌으므로 문항을 참조하는 코드에 **도달조차 못 하게** 한 곳으로 좁힌다.
- 🔴 **DB row를 통째로 펼쳐서 내려보내지 않는다.** 필드를 하나씩 골라 담는다 — 컬럼을 추가할 때
  조용히 새는 유일한 경로다.
- 🔴 **마이페이지를 서버 컴포넌트로 만들어 문항을 props로 넘기지 않는다.**
  `import "server-only"`는 **번들 포함만** 막지 서버가 클라이언트로 보내는 데이터는 못 막는다.
  클라이언트가 `GET /api/me/[token]`으로 가져오게 한다.
- ⚠️ `biz.ts`를 **신원**과 **계좌** 둘로 쪼갠다. 지금은 토큰만 맞으면 계좌가 항상 내려간다.

## 7. 운영자 페이지

`Board.tsx`는 **버린다**(상태 9개 전제라 남는 게 거의 없다). 셋은 반드시 가져온다:
`admin.module.css` 전부 · **누가 눌렀는지를 다루는 패턴**(하이드레이션 불일치 회피, 실측 근거가
주석에 있다) · **서버가 첫 데이터를 넘기고 30초마다 갱신.**

- **사용자 관리** — 목록(상태 · 이름 · 성별 · 나이 · 연락처 · 신청일 · **기한** · 마지막 발송)
  + 검색 · 필터 + 일괄선택 → 상세 서랍(답변 · 돈 줄 · 발송 이력 · 조작 로그 + 수정 폼)
- **입금 확인** — 입금자명 · 금액 · 입금 시각 · 확인한 사람. 🔴 금액이 39,000원이 아니어도
  **막지 않는다**(막으면 운영자가 시스템 밖에서 처리하고 기록이 사라진다). 다르면 표시만 남긴다.
  「입금완료로 바꾸기」와 「돈 줄 쌓기」는 **버튼 하나**로 같이 일어난다 — 따로 두면 하나만 하고 잊는다.
- **닉네임 배정** — 행사 며칠 전, 확정된 스무 명에게 1~20을 한 번에 붙이는 버튼
- **마케팅** — 유입(`source`·`utm`) · 퍼널(신청 → 정식등록 → 입금 → 사전질문)
- **알림톡** — 여러 명 체크 → 문구 선택 → 개인별 미리보기 → 발송.
  상단에 **「오늘 보낼 것」**과 **「보내다 실패한 것」**
- **문구 관리** — 알림톡 문구 CRUD

🔴 `prompt()`/`confirm()` **전부 제거.** 모바일에서 차단되고 입금액을 문자열로 받아 검증이 안 된다.
🔴 **누가 눌렀는지 필수** — 운영자 셋이 비밀번호를 공유해 쿠키로는 알 수 없다.

## 8. 이 결정이 기대는 것 (깨지면 결정도 깨진다)

- 🔴 **「오늘 보낼 것」 · 「보내다 실패한 것」 목록.** 자동화가 입금 안내 하나뿐이므로 운영자가

  화면이 대신 기억한다.
- 🔴 **운영자 목록의 「기한」 칸.** 자동 만료가 없어진 지금 더 중요해졌다. 남은 시간과
  12시간 미만 강조를 반드시 옮긴다.
- 🔴 **`db.ts`의 `max: 10`.** 선착순이 사라졌다고 동시성이 사라진 게 아니다 — 인스타 게시물
  직후 신청이 몰리는 것은 그대로다(`max:1`에서 27건 중 8건 사망, 2026-08-29 실측).
- 🔴 **`middleware.ts`**(`/admin/:path*`, `/api/admin/:path*`). 지금은 라우트마다 손으로
  막는데 하나만 빠뜨리면 참가자 20명의 이름 · 연락처 · 생년월일이 샌다.
  라우트별 확인은 이중 방어로 남긴다.
- 🔴 **`/api/recruit`만 `{ok,data}` 봉투를 씌우지 않는다.** `RecruitStatus.tsx:31`이 최상위에서
  값을 읽고 없으면 **에러 없이 아무것도 안 그린다** — 홈의 「모집 현황」 줄이 조용히 사라진다.
- 🔴 **`SiteChrome.tsx`에 `/me/`를 추가한다.** 안 하면 마이페이지에 헤더와 「1차 모임 신청」
  고정 바가 붙어, 이미 신청한 사람에게 다시 신청하라고 권하는 화면이 된다.
- 🔴 **`admin-data.ts`를 1단계에서 함께 지운다.** 사라지는 표를 조인하므로 남겨두면
  **빌드와 타입 검사는 전부 통과하고** 런타임에 `/admin`이 통째로 500이 된다.
- 옛 주소 `/pre/[token]`·`/q/[token]`는 **그냥 지운다** — 신청자가 0명이라 밖에 나가 있는
  링크가 없다.
