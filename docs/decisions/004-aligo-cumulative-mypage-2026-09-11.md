## 2. 🔴 카카오가 ①을 반려했다 (2026-09-11)

여섯 개를 심사에 올렸고 **①이 반려됐다.** 사유를 그대로 옮긴다.

> 메시지 내 확인되는 링크가 **결제 링크일 경우** 금융사고 예방 목적으로
> 결제·송금·납부 유도 메시지를 허용하지 않는다. **결제 링크가 아닐 경우,
> 오인 소지가 없도록 해당 고정값을 추가**하라. 예: `신청 확인 하기▶ #{링크}`

**우리는 결제 링크가 아니다.** 마이페이지에는 결제 기능이 없다. 계좌와 금액을 **보여주기만**
하고 손님이 자기 은행 앱에서 이체한다. 카카오 기준도 「무통장 입금 등 경로 또는 방법
안내는 가능」이라고 명시한다. 그래서 증빙을 준비할 필요 없이 고정값만 붙이면 된다.

🔴 **여섯 개 전부 고쳤다.** ①만 반려됐지만 나머지도 같은 모양이라 같은 사유로 걸린다.
손으로 보내는 넷도 같은 표기로 맞췄다 — 두 벌이 되면 하나가 낡는다.

| | 전 | 후 |
|---|---|---|
| ① ② ③ | `▶ #{링크}` | `▶ 신청 내용 확인하기 #{링크}` |
| ④ ⑤ | 〃 | `▶ 사전 질문 답하기 #{링크}` |
| ⑥ | 〃 | `▶ 안내 다시 보기 #{링크}` |
| ⑦ | 〃 | `▶ 남기러 가기 #{링크}` |
| ⑧ | 〃 | `▶ 연결 안내 확인하기 #{링크}` |
| ⑨ | 〃 | `▶ 리포트 보기 #{링크}` |
| ⑩ | 〃 | `▶ 환불 내역 확인하기 #{링크}` |

①에서 「링크에서 참가 정보를 입력하고 **입금해 주세요**」도 뺐다. 링크에 결제 기능이
있다는 뜻으로 읽힌다. 「아래에서 신청 내용과 **입금 안내를 확인해** 주세요」로 바꿨다.

## 3. 마이페이지를 별도로 배포하지 않는 이유

소유자가 「별도 배포하거나 카카오 로그인을 붙이면 어떤가」를 물었고, 검토 결과 **지금
레포에 그대로 두기로** 했다. 근거 셋.

1. 🔴 **방어선이 두 벌이 된다.** 계좌를 정식등록 전에 막는 장치(`me-screen.ts`의
   `guardExposure`, `biz.ts`의 신원·계좌 분리)와 문항을 입금완료 전에 응답에 안 싣는
   장치(`form9-copy.ts`의 `server-only` + 화면별 필드 선별)가 이 레포 코드에 묶여 있다.
   쪼개면 같은 규칙을 두 곳에서 지켜야 하고, **한쪽만 고치는 순간 새는 쪽이 생긴다.**
2. **주소를 바꾸면 알림톡을 다시 심사받는다.** 여섯 개가 전부 링크 변수 하나만 쓴다.
3. **카카오 로그인은 마찰이 더 크다.** 채널 친구 추가와 동의가 붙고, 신청할 때 적은
   연락처와 카카오 계정이 다른 사람이 반드시 생긴다. 스무 명 규모에서는 토큰 링크가 싸다.

## 4. 🔴 닉네임 — 소유자 지시와 지식베이스 정본이 부딪친다

소유자 지시는 **「손님이 자기 닉네임을 정하고 그 값이 DB에 저장되게 한다」**이다.
**구현 전에 이 절을 먼저 읽어야 한다.**

### 지금 규칙과 그 근거

`CONTEXT.md`와 003 결정 14는 **운영자가 행사 며칠 전 1~20을 한 번에 붙인다**고 정했고,
DB도 그렇게 잠겨 있다(`nick smallint check (nick between 1 and 20)` + 회차별 유일).

지식베이스는 한 걸음 더 나간다. 운영 매뉴얼과 제작물 사양집이 **세 곳에서** 같은 말을 한다.

> **무작위 배정** — 신청·도착 순서와 무관. 순서가 새어나가지 않는다.
> **성별과 번호 무관** — 남녀 각 열 명이 섞여 배정된다. **번호로 성별을 맞힐 수 없어야 한다.**
> 「결돌이/결순이」가 아니라 「결N」인 이유는 **호칭 자체가 성별을 부르면 안 되기** 때문이다.

사양집은 데모 데이터의 성별표까지 일부러 불규칙하게 박아 두고 경고를 달았다 —
**「예시가 규칙적이면 그대로 구현돼 규칙이 무너진다.」**

### 그래서 무엇이 깨지는가

| 깨지는 것 | 왜 |
|---|---|
| **성별 은폐** | 손님이 고른 말은 성별을 드러낸다. 기계로 못 막는다 |
| **본명 비공개** | 모임 전날 안내의 그라운드룰 첫 줄이 「이름을 말하지 않습니다」다. 실명을 닉네임으로 적으면 첫 줄부터 깨진다 |
| **컬럼 타입** | 지금은 숫자다. 글자를 넣을 수 없다 |
| **명찰·페어링** | 생성기가 D-1에 닉네임과 짝을 **함께** 만든다. 시드를 바꾸면 명찰·비교표·로테이션 표가 서로 어긋난다 |

### 결정 — 번호는 남기고 칸을 하나 더 만든다

- 숫자 번호(`nick`)는 **그대로 둔다.** 명찰 인쇄 순서와 짝 맞추기가 여기 기댄다.
- 손님이 고른 글자를 담을 **새 칸**을 만들고 화면과 현장 표기에 쓴다.
- 🔴 **제약 넷을 반드시 건다** — 회차 안에서 유일 · 신청 때 적은 본명과 같으면 거절 ·
  길이와 글자 종류 제한(이름표에 인쇄된다) · 성별이 드러나지 않도록 안내와 운영자 검토.
- 🔴 **행사 당일 전까지만 고칠 수 있다.** 좋아요를 받은 뒤에 바뀌면 연결 결과가 엉킨다.

⚠️ **성별 은폐는 기계로 지킬 수 없다.** 이 결정은 그 보호를 **사람의 검토로 낮춘다.**
지식베이스 쪽 문서(운영 매뉴얼 §2.4, 사양집 §1)도 이 결정에 맞춰 고쳐야 한다 —
안 고치면 현장에서 두 규칙이 부딪친다.

## 5. 알리고 규격 — 003 §3을 대체한다

2026-09-11 공식 문서 원문 실측(`smartsms.aligo.in/alimapi.html`·`smsapi.html`).

### 뿌리오와 다른 점

| | 뿌리오(옛) | 알리고 |
|---|---|---|
| 본문 | JSON | 폼 인코딩 |
| 인증 | 계정·비밀번호로 토큰 → 헤더 | 키·아이디·토큰을 **본문에 함께** |
| 성공 | 접수 코드 1000 | 응답 코드 0 |
| 도달 | 웹훅으로 밀어 줌 | 🔴 **웹훅 없음.** 조회만 |

### 되돌리면 깨지는 것 여섯

- 🔴 **알림톡과 문자는 서로 다른 서비스다.** 주소도 다르고 **인증 파라미터 이름도 다르다.**
  하나의 클라이언트로 뭉치지 말 것.
- 🔴 **성공 코드가 엔드포인트마다 다르다.** 알림톡 발송은 0, 문자 발송과 잔액 조회는 1.
  **HTTP는 실패해도 항상 200으로 온다.** 「코드가 0이면 성공」을 공통으로 쓰면 문자가
  전부 실패로 기록된다.
- 🔴 **접수 코드가 성공이어도 실패 건수가 있을 수 있다.** 성공/실패 건수를 함께 본다.
- 🔴 **본문이 심사에 올린 템플릿과 개행 한 칸까지 같아야 한다.** 다르면 발송되지 않고,
  그 사실이 **접수 응답이 아니라 도달 조회에서만** 드러난다. 도달 조회를 안 만드는
  결정과 겹치면 **조용히 아무것도 안 나가는** 상태가 된다. 아래 「올리기」가 이걸 막는다.
- 🔴 **서버가 여러 대면 토큰을 공유할 수 없다.** 토큰에 서버 정보가 들어 있다고 문서가
  못박았다. Vercel은 인스턴스가 여럿이므로 인스턴스마다 자기 토큰을 갖게 둔다.
- ⚠️ **공식 에러 코드 표가 없다.** 문서가 「메시지 문구를 참고하라」고만 적었다.
  **문자열로 분기하지 않는다** — 대행사가 문구를 바꾸는 순간 깨진다. 그대로 기록만 한다.

### 템플릿을 코드로 올린다

템플릿을 만들고 고치고 지우고 **심사를 요청하는 것이 전부 API로 된다.** 심사 요청은
오히려 **API로만** 된다. 문구 관리 화면에 셋을 붙인다.

1. **올리기** — DB의 문구를 그대로 읽어 등록한다. 올린 것과 보낼 것이 같은 한 줄에서
   나오므로 위의 「개행 한 칸까지」 위험이 구조적으로 사라진다.
2. **심사 요청**
3. **상태 가져오기** — 등록 / 심사중 / 승인 / 반려와 **반려 사유**, 승인 코드를 받아온다.
   DB의 심사 상태 칸이 알리고가 쓰는 값과 글자까지 같아 그대로 받아 적으면 된다.
   ⚠️ 이미 화면에서 손으로 올린 여섯 개도 같은 목록으로 돌아오므로 그대로 보인다.

### 문자로 나갈 때

⚠️ 90바이트를 넘으면 자동으로 장문이 된다(우리 문구는 전부 넘는다). 문제는 값이 아니라
**글자가 깨지는 것**이다 — 통신사 문자 시스템이 옛 한글 인코딩을 쓰므로 특수문자가
물음표로 바뀔 수 있다고 문서가 경고했다. 🔴 **우리 문구에 실제로 위험이 있다** —
모든 문구가 링크 앞에 화살표를, 목록에 가운뎃점을 쓴다. **내보내기 전에 한 통을 받아 본다.**

### 발송 시각

개발자 전달 문서가 20시 이후 발송을 금지하며 「법이 걸린 부분」이라고 적었다.
⚠️ **근거를 바로잡아 둔다** — 법정 야간 제한은 **21시부터 다음 날 8시까지이고 광고성
정보에만** 걸린다. 우리 열 개는 전부 정보성이라 법으로는 해당이 없다. 20시 규칙은
법이 아니라 운영 판단이다. **그래도 지킨다** — 신고가 쌓이면 소명과 무관하게
**사업자등록번호 단위로 영구 차단**되고, 그러면 2차·3차 회차도 못 쓴다.

| 신청 접수 | 언제나 |
| 대기 안내 | 자리가 찼을 때 |
| 참가 정보 입력 | 언제나(대기자 포함) |
| 입금 안내 | 정식등록을 마쳤을 때 |
| 사전 질문 | 입금완료일 때 |
| 모임 안내 | 입금완료일 때 |
| 현장에서 쓸 폼 | 행사 당일 |
| 마음에 든 분 남기기 | 행사 다음 날부터 마감까지 |
| 연결 결과 | 마감 뒤, 서로 고른 쌍에게만 |
| 리포트 | 리포트가 나온 뒤 |
| 취소 안내 | 취소됨일 때. **이 단계만 남고 나머지는 전부 닫힌다** |

### 🔴 노출 규칙은 하나도 느슨해지지 않는다

003 §6의 정보 노출 표가 **그대로 살아 있다.** 화면이 하나에서 목록으로 바뀌었을 뿐이다.

- 계좌는 정식등록을 마쳐야 목록에 남는다.
- 문항은 입금완료여야 목록에 남는다. **문항 방어의 실체는 토큰이 아니라 「입금완료」다.**
- 취소된 사람은 계좌·문항 단계가 통째로 빠진다.
  🔴 **정식등록을 마친 취소자에게서 계좌가 샌 조합이 실제로 있었다**(`me-screen.ts` 주석).
  목록형에서도 같은 조합을 검사한다.
- **DB 행을 통째로 펼치지 않는다.** 반복문으로 바뀌면 「한 번에 다 담자」는 유혹이 생긴다.

### 운영자 화면 고정의 뜻이 바뀐다

003 결정 13은 살아 있다. 다만 「이 화면만 보여준다」가 **「이 단계를 펼친 채로 연다」**가
된다. 컬럼(`view_override`)과 API는 그대로 쓴다.
🔴 **노출 규칙은 여전히 고정보다 세다.**

## 7. 행사 당일과 그 뒤 — 새로 만드는 것

지식베이스의 폼 번호로는 10·11·12·13이 「현장에서 쓸 폼」이고 14가 「마음에 든 분 남기기」다.
**종이 폼은 하나도 없다** — 응답을 받는 물건은 전부 참가자 본인의 휴대폰이다.

### 🟢 데이터 모델은 이미 자리가 잡혀 있다

`answer` 표가 처음부터 이걸 염두에 두고 만들어졌다. 폼 이름 칸과 라운드 번호 칸이 따로
있고, 라운드가 엉뚱한 폼에 섞이지 않도록 DB가 막는다. 부분 잠금이 두 개 걸려 있어
중복 제출이 뚫리지 않는다. **새 표를 만들 일이 거의 없다.**

### 되돌리면 깨지는 것 다섯

- 🔴 **1부 회차 평가는 덮어쓰지 않는다.** 라운드마다 한 번, 두 번째 제출은 거절한다.
  덮어쓰면 어느 것이 진짜인지 영원히 알 수 없다. **메모만 나중에 덧붙일 수 있다.**
- 🔴 **좋아요만 고칠 수 있다.** 마감 전까지 바꿀 수 있는 것이 이 폼의 정의다 —
  한 번 누르면 끝이면 숙고가 아니다. 나머지 폼은 전부 한 번뿐이다.
- 🔴 **상대 명단을 클라이언트에서 거르지 않는다.** 서버가 **반대 성별 열 명만** 내려준다.
  화면에서 거르면 응답에 전원 명단이 실려 나가 **성별이 드러난다.**
- 🔴 **결과를 절대 보여주지 않는다.** 누가 나를 골랐는지도, 중간 집계도 안 된다.
  한쪽만 고른 경우는 **어느 쪽에도 알리지 않는다.** 미매칭자에게는 아무것도 보내지 않는다 —
  「아쉽게 연결되지 않았습니다」는 위로처럼 보이지만 미선택 통보다.
- 🔴 **전화번호를 교환하지 않는다.** 오픈채팅 링크나 인스타 계정만 주고받는다.
  둘의 선택이 갈리면 **더 익명적인 오픈채팅**으로 연다. 번호는 한쪽이 불편해도 회수가 안 된다.

### 제3자 제공 동의

🔴 **동의하지 않으면 서버가 연결을 만들지 않는다.** 「연결은 원하지 않습니다」를 고르면
동의를 **아예 묻지 않는다** — 필요 없는 동의를 받는 것도 문제다.
🔴 **동의 시각을 따로 남긴다.** 이 폼은 마감 전까지 고칠 수 있어 **제출 시각과 동의 시각이
실제로 다르다.** 껐다 다시 켜면 마지막에 켠 시각으로 갱신한다.
고지 항목 다섯 가지(제공받는 사람·제공 항목·목적·기간·거부권)를 화면에서 줄이지 않는다.

### ⚠️ 지식베이스에 없는 것 — 연결 결과 화면

**「연결 결과」 화면의 사양이 지식베이스 어디에도 없다.** 알림톡 ⑧이 「상대 이름은 문구에
넣지 않고 마이페이지에서 보여주는 편이 안전하다」고 넘겨 놓았는데, 그 화면이 무엇을
보여주는지가 정의돼 있지 않다. 문안 재료는 운영 매뉴얼의 매칭 통보 문안 두 가지뿐이다.
**구현 전에 소유자와 이 화면을 정한다.**
